# V1.9 — Evidence-bound causal state machine

## Scope

This increment adds a deterministic, bounded discrete-event state machine. It is intentionally narrower than a general causal discovery system or a continuous-time physics solver. It does not infer causal links from co-occurrence, correlation, or an algebraic dependency graph.

A transition is treated as an explicit intervention rule supplied in the source evidence: when the model is in a declared source state and receives a declared event, the transition may move it to a declared target state if its guard is satisfied.

## Source syntax

Declarations are isolated clauses in a saved knowledge anchor's `evidenceQuote`:

```text
state(off)；
state(on)；
initial(off)；
transition(off,power_on,on)；
transition(on,power_off,off)。
```

Numeric guards and invariants:

```text
state(idle)；
state(heating)；
state(boiling)；
initial(idle)；
input(T)=K；
transition(idle,start,heating)；
transition(heating,heat,boiling):T>=373；
invariant(T>=0)。
```

- `state(name)`: declares one discrete state.
- `initial(name)`: declares exactly one initial state.
- `input(name)=unit`: declares an observed numeric input and its unit label.
- `transition(from,event,to)`: declares an event-triggered transition.
- `transition(from,event,to):input>=constant`: adds a numeric guard.
- `invariant(input>=constant)`: condition checked on every event step.

Identifiers start with a letter and contain at most 24 ASCII letters, digits, or underscores. Events and states are case-sensitive. The grammar supports `>`, `>=`, `<`, `<=`, `=`, and `==` comparisons against finite constants in ±1,000,000.

## Execution contract

The API compiles the model from the server-stored anchor, then executes a caller-supplied ordered list of 1–40 event steps. Every step supplies the event name and all declared numeric inputs. Execution starts at the model's declared initial state. Each step:
1. validates exact input keys and finite numeric bounds;
2. checks all invariants;
3. finds transitions matching the current state and event;
4. evaluates guards;
5. performs exactly one eligible transition.

No matching transition, a blocked guard, a violated invariant, or multiple simultaneously eligible transitions causes an explicit error. The engine never chooses a transition based on source order. The complete trace includes event, prior state, next state, supplied inputs, matched rule, and guard.

The endpoint is stateless: a run does not write palace data, learning history, or user progress. Replaying the same source revision and inputs produces the same trace. Changing the source invalidates the previous revision.

The dedicated `state-machine.html` workspace displays declared states, transitions, guards, and invariants. Users choose a saved palace anchor, construct an ordered event sequence, enter the required values for each step, and inspect the resulting trace. The palace sidebar and selected-anchor inspector link to this workspace.

## Units and scientific interpretation

Input unit strings are labels, not a unit algebra. A guard threshold is interpreted in the same declared unit as its input. The state-machine module does not convert units, prove dimensional consistency, or verify that the user chose the correct unit. The separate unit-aware formula compiler is responsible for algebraic dimensional checks.

The machine is discrete-event only. It does not model continuous-time integration, differential equations, stochastic transitions, hidden states, or numeric state assignments. A state transition is an explicit intervention rule, not proof that the event is a real-world cause.

## Safety bounds

- Maximum 12 states, 8 numeric inputs, 24 transitions, and 12 invariants.
- Maximum source evidence: 2,000 characters.
- Maximum 40 steps per run.
- Input and comparison constants are finite and bounded.
- No model-generated JavaScript, `eval`, dynamic import, or arbitrary code execution.
- Unsupported or ambiguous models fail closed.

## API

- `GET /api/palaces/:palaceId/state-machines/:conceptId`: compile and inspect the state machine.
- `POST /api/palaces/:palaceId/state-machines/:conceptId/run`: run an ordered trace.

Example request:

```json
{
  "revision": "<revision returned by GET>",
  "steps": [
    {"event":"power_on","inputs":{}},
    {"event":"power_off","inputs":{}}
  ]
}
```
